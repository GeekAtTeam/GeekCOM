# Tauri 接收显示性能优化

更新：2026-09-28。性能优化已提交为 `c77659c`（基于 `539d3a5`）。对照方法和旧版结果见 [测试计划](performance-test-plan.md) / [性能基线](performance-baseline.md)。本轮未修改 Qt 或 Rust 串口读写逻辑，未向真实设备发送数据。

## 与 Qt 的比较结论

本文“旧版 / 原实现”指优化前的 Tauri，不是 Qt。既有 60 秒基线中，Qt 调试 / 终端显示 P95 分别为 305 / 36 ms，优化后的 Tauri 为 48–49 / 43–44 ms。当前调试实现改善明显；终端差距小于 16 ms 观察间隔，不据此宣称明显体验差距。Qt 终端 CPU 估计约 39% 单核，Tauri 约 56–59%，仍有资源优化空间。

两者历史容量、终端能力与观测开销不完全一致；RSS 进程树求和包含共享页重复计算和自动化进程。上述比较不代表框架性能上限，也不构成精确的内存倍数比较。

## 长时间验证（2026-09-24）

长测工具先做以下调整，产品二进制保持不变：

- WebView 每 10 秒将延迟样本取回 Python，清空已取回数组，并限制去重集合为最近 8,192 个标记，避免测试仪器本身在 WebView 内无限积累记录。完整样本仍保留在测试主机进程中。
- 资源样本使用单调时钟的真实经过时间，CPU 估算使用真实采样跨度。
- 每分钟落盘进度和资源轨迹；最终报告按发送序号所属分钟汇总延迟，便于发现后段退化。

取回样本会增加少量 WebDriver 开销，新的长测结果应标明此测量方式；RSS 仍是包含自动化的进程树求和，不能直接据此判定产品泄漏。

长测已完成，2026-09-28 核对原始报告。测试于 2026-09-24 23:38（UTC+8）启动，调试、终端顺序各运行 3,600 秒，96 B × 100 Hz（9,600 B/s），仅使用新建 PTY。环境为 Linux x86_64 / glibc 2.39，Release 产品提交 `c77659c`，测量脚本包含本节所述尚未提交的改动。

工具冒烟先行通过：两模式各 65 秒，均观察到 6,500 / 6,500 个唯一标记，输入与 RX 均为 624,000 字节，无发送背压，调试 / 终端 P95 为 48 / 43 ms。原始结果：`benchmark-results/soak-harness-smoke-20260924/results.json`。

每模式发送 360,000 个标记，输入与界面 RX 计数均为 **34,560,000 字节**，无发送端背压。以下延迟统计仅覆盖观察到的标记。

| 未观察标记 | 643 | 0 |

| 最大延迟 | 596 ms | 70 ms |

### 结论与限制

- 两模式在该负载下均完成长时接收，RX 计数与输入一致，前后段及每分钟 P95 未见明显累积退化。这不等于逐字节内容完整性验证，也不证明界面始终显示了所有输入。
- 调试模式存在 643 个未观察标记和一次或多次较长停顿，最大观察延迟 596 ms、采样间隔最大 538 ms。当前证据不能区分采样漏观测、可见内容滚出及显示链路问题，需继续定位；不能标为全部显示验收通过。
- RSS 是包含自动化进程且可能重复计算共享页的进程树总量；记录值未见超过上述峰值，但不能仅凭此认定无内存泄漏。需结合 PSS、进程生命周期及关闭观测的对照进一步判断。
- 断开数据是每模式结束后各一次观测，包含 WebDriver 往返，不是持续接收中断开的 P95；本轮没有长时重连与实机拔插验证。
- **长测执行完成，但迁移验收未全部通过。** 真实 IMU、ANSI 密集流、其他平台以及 100 字节 × 1 kHz（100,000 B/s）均未在本轮验证，暂不据此替代 Qt 主分支。

原始报告：`benchmark-results/soak-20260924/results.json`；运行日志：同目录 `runner.log`；分钟进度：`tauri-debug-progress.json` / `tauri-terminal-progress.json`。进度文件保留的是最后一个周期快照，最终结果以 `results.json` 为准。原始产物目录受 Git 忽略，本 Markdown 保存可审阅的摘要。

## 定位依据

均为本机 Release，96 字节 × 100 Hz、60 秒、自动滚动，时间戳默认开启。

| 实验 | 调试显示 P95 | 后段 P95 | 观察到的标记 |
|---|---:|---:|---:|
| 原实现 | 1348 ms | 1515 ms | 5656 / 6000 |
| 仅缓存 React 日志行，仍保留全部历史节点 | 1287 ms | 1394 ms | 5874 / 6000 |
| 动态高度虚拟列表，仍使用原 40 ms 轮询 | 54 ms | 54 ms | 6000 / 6000 |

与关闭时间戳的前轮实验结合，证据支持优先减少历史 DOM 和布局工作。不能将根因笼统归为 Rust、IPC 或 Tauri；本轮也没有做浏览器 CPU 火焰图，所以不声称已经分离出每个浏览器内部阶段的耗时。

## 最终实现

- `ui/src/LogRows.tsx` 使用 [TanStack Virtual](https://tanstack.com/virtual/latest/docs/api/virtualizer) 按可见区域及两侧各 8 条缓冲渲染，动态测量多行内容。事件 ID 用于定位和选择，格式/宽度变化会重新测量；旧记录淘汰时同步释放高度缓存。
- 原始历史仍在 App 的有界存储中，导出遍历保留记录。没有通过减少 4,000 条 / 2 MiB 上限或丢弃新记录获得性能改善。
- 接收轮询仍保持最多一个在途请求：调试 32 ms，终端 16 ms，未连接 100 ms。间隔指请求完成后的等待时间，不是保证的画面帧率。
- RX/TX 等计数最多每 100 ms 更新一次界面；连接、会话、错误、发送任务启停和溢出提示立即更新。避免无变化状态反复渲染整个工作台。
- 同批终端读取块按原顺序合并后交给 xterm；保留会话/连接切换的迟到响应保护。

两种模式都采用 16 ms 的中间版本虽将 P95 降至调试 38 ms、终端 43 ms，但本机进程树 CPU 估计约 76% / 66% 单核。最终为调试保留约 30 次/秒刷新，并将计数刷新与接收解耦；没有仅追求轮询频率。

## 验证范围

- 构建：TypeScript / Vite、Rust Release 可执行文件成功。
- 前端：7 项模型测试、10 项界面回归全部通过；新增大历史下的暂停/恢复、选择、格式切换、淘汰和完整导出检查。
- 原生：真实 Tauri IPC + PTY 的文本/HEX、跨块中文、周期发送、持续接收中断开、句柄释放、终端设备状态响应及模拟拔出通过。
- 本轮原生文件对话框与截图显式跳过，没有将它们写成通过；原生测试未访问真实 IMU。
- 与旧基线相同，延迟是带 16 ms 观察误差的“文本可用时间”，不是像素绘制时间。虚拟列表只暴露可见附近的 DOM，未观察标记不能直接等于设备丢字节；对照同时保留输入量和 RX 总数。
- 本节为短测验证范围；60 分钟补测结果见上文。真实 IMU、ANSI 密集负载和其他操作系统仍未验收，不能据此宣布可以移除 Qt。

## 测试异常与产物保留

- Vite 开发服务器曾遇到系统文件监听资源限制，界面回归改用已构建的 `vite preview` 执行，没有修改系统限制或关闭用户进程。
- 第一次终端交互场景在连接阶段超时，尚未开始发送或测量。独立重跑通过（9 次操作，P95 约 21 ms），但此次无法确定偶发超时的原因，不能直接归因于桌面环境，也没有把该失败试次计为通过。后续补跑也出现过同类超时，页面无串口错误提示。脚本原先等待输入框可用后再独立点击连接，存在启动枚举重新禁用按钮的时序窗口；现改为同一 JS 任务检查实际连接按钮再点击，不会对已提交的连接重复点击。原失败记录仍保留，不能将全部历史失败武断归为框架问题。
- 前期与上述三轮的原始产物放在 `test-results/`，后续 Playwright 自动清理了该目录。上表保留当时的工具输出汇总，不能将旧路径声称为仍可访问的完整样本。
- 现已改用独立且受 Git 忽略的 `benchmark-results/`，并对最终二进制重新采集一轮两模式基线和交互场景；完整样本、参数、驱动日志及二进制哈希保存在下文列出的目录。后续界面回归不会清理它们。
